ENEL 573 Ch5 Transport Layer

How data gets from one process to another across the Internet: steering segments to the right socket with port numbers, UDP and its checksum, TCP's byte-numbered sequence numbers, ACKs and retransmissions, flow control, opening and closing connections, and TCP congestion control with slow start, AIMD and the reaction to loss. Every lecture example is worked step by step.

Start hereBig picture

The network layer (IP) moves datagrams from one host to another, and it makes no promises: packets can be lost, reordered or corrupted. But the things that actually talk are processes (a browser tab, a mail client, a DNS resolver), and several of them run on each host. The transport layer closes both gaps. It runs only on the end systems, delivers each segment to the right process using port numbers, and (in TCP's case) builds a reliable, ordered byte stream that does not swamp the receiver or the routers in between.

The chapter moves from the simplest service to the most complete one. First, how a host decides which socket gets a segment. Then UDP, which adds almost nothing beyond that plus a checksum. Then TCP: numbering bytes, acknowledging them, retransmitting what is lost, keeping the receiver's buffer from overflowing, and setting up and tearing down connections. Finally, how TCP senses congestion in the network and adjusts its sending window.

Part 1 · Services and demultiplexing

Section 1Transport layer services

The transport layer gives logical communication between application processes running on different hosts. "Logical" means each process acts as if it had a direct pipe to the other one, even though the data actually crosses many routers. Transport protocols run only on the end systems; routers in the middle look at the network-layer header and never at the transport header.

On the sending side, the transport layer breaks each application message into segments (adding its own header to each) and passes them down to the network layer. On the receiving side, it reassembles segments into messages and passes them up to the application.

The network layer gives logical communication between hosts; the transport layer gives logical communication between processes. The transport layer relies on the network layer's service and enhances it. The Internet offers applications two transport protocols:

ProtocolDeliveryExtra services
TCPreliable, in-ordercongestion control, flow control, connection setup
UDPunreliable, unorderednone: a simple extension of "best-effort" IP

Two services are available from neither protocol: delay guarantees and bandwidth guarantees. IP underneath is best effort, so no transport protocol running only on the end systems can promise them.

\[ \text{segment} = \text{transport header} + \text{chunk of the application message} \]
what the transport layer hands to the network layer
segment = the transport-layer packet, in bytes (B) · transport header = port numbers and other control fields added by TCP or UDP, in bytes (B) · application message = the data a process writes into its socket, in bytes (B)

Analogy

TCP is like a phone call: you dial first (connection setup), the other person confirms what they heard, and if a sentence is garbled you repeat it. UDP is like dropping postcards in a mailbox: no setup, no confirmation, and a lost card is simply lost. The analogy breaks down on ordering: a phone call is naturally in order, while TCP has to rebuild order from segments that may arrive scrambled.

Tricky bits
  • Host to host is the network layer; process to process is the transport layer. Exams like to swap these.
  • Routers do not run TCP or UDP. Transport protocols run on end systems only.
  • TCP gives reliability and ordering, but not guaranteed delay or bandwidth. Neither does UDP.
  • UDP is "unreliable", but it still has a checksum to detect errors (Section 6). Unreliable means no recovery, not no checking.
Practice 1.1 (not from the lecture): a video call that needs 5 Mb/s

A video-call app needs a guaranteed 5 Mb/s path and a guaranteed one-way delay below 100 ms. Which Internet transport protocol provides this?

Neither. TCP adds reliability, ordering, flow control and congestion control; UDP adds only port-based delivery and a checksum. Both run on top of best-effort IP, which makes no promise about bandwidth or delay.

Section 2Multiplexing and demultiplexing

A host may run many processes that use the network at once, and each process talks to the network through one or more sockets (the "door" between the process and the transport layer). Two jobs follow:

  • Multiplexing (at the sending host): gather data from multiple sockets, wrap each chunk with a header that will later be used for demultiplexing, and pass the segments to the network layer.
  • Demultiplexing (at the receiving host): deliver each received segment to the correct socket.

How does the receiver know which socket? Each IP datagram carries a source IP address and a destination IP address, and carries exactly one transport-layer segment. Each segment carries a source port number and a destination port number in the first 32-bit row of its header. The host uses the IP addresses and port numbers together to direct the segment to the right socket. Both TCP and UDP segments start with this same pair of port fields.

\[ \text{ports per host} = 2^{16} = 65\,536, \qquad 0 \le \text{port} \le 65\,535 \]
each port field is 16 bits
port = a 16-bit number that identifies a socket on a host (no unit) · \(2^{16}\) = number of distinct values a 16-bit field can hold (no unit)
Filled in

The lecture's segment format shows the source and destination port fields side by side in a row labelled "32 bits" but does not state their individual size. Two equal fields in a 32-bit row are 16 bits each, which gives the 0 to 65 535 range above.

Example 2 (lecture): three hosts, four processes
Host 1 runs process P3, host 2 runs P1 and P2, host 3 runs P4. Each process has one socket. P3 talks to one process on host 2 and P4 talks to the other.

Host 1 and host 3 each multiplex: the transport layer takes data from the socket, adds a header with source and destination port numbers, and hands the segment to the network layer.

Host 2 receives both streams through one network interface. Its transport layer reads the port numbers in each segment and demultiplexes: segments from P3 go up to one socket, segments from P4 go up to the other, so P1 and P2 each get only their own data.

When P1 and P2 reply, host 2 multiplexes their two sockets back into its single network layer.

Multiplex on send (many sockets in), demultiplex on receive (one stream out to the right socket)
Analogy

An apartment building's mailroom. Outgoing letters from every flat go into one mailbag (multiplexing); incoming letters all arrive in one bag, and the clerk sorts them into flat mailboxes by flat number (demultiplexing). The street address is the IP address and the flat number is the port. The analogy breaks for TCP, where the clerk also looks at who sent the letter (Section 4).

Tricky bits
  • Multiplexing is at the sender, demultiplexing at the receiver.
  • The row is 32 bits wide, but each port is 16 bits. The largest port number is 65 535, not 65 536 (counting starts at 0).
  • One IP datagram carries one transport segment; demultiplexing uses fields from both headers (IP addresses from the IP header, ports from the segment header).

Section 3Connectionless demux (UDP)

A UDP socket is created with a host-local port number, for example in Java:

DatagramSocket mySocket1 = new DatagramSocket(12534);

When a process sends a datagram into a UDP socket, it must specify the destination IP address and destination port number. When a host receives a UDP segment, it checks only the destination port number in the segment and directs the segment to the socket with that port number. So a UDP socket is identified by a 2-tuple:

\[ \text{UDP socket} \;\leftrightarrow\; (\text{dest IP address},\ \text{dest port}) \]
all segments with the same destination IP and port reach the same socket
dest IP address = 32-bit address of the receiving host (no unit) · dest port = 16-bit port number of the receiving socket (no unit)

Consequence: UDP segments with different source IP addresses or source ports but the same destination IP and port are delivered to the same socket. The source port is still carried, because it is the "return address" the receiver uses when it replies.

Analogy

A single public suggestion box: anyone can drop a note in it, and all notes land in the same box. If a writer wants an answer, they write their own address on the note (the source port). The analogy breaks a little because the box owner here does not need to know who wrote the note to accept it; UDP never checks the sender before delivery.

Tricky bits
  • UDP demux uses only the destination IP and destination port. Source fields do not change which socket receives the segment.
  • In a reply, the ports swap: reply SP = request DP, reply DP = request SP.
  • "Connectionless" means no handshaking; it does not mean the segment has no source port.

Section 4Connection-oriented demux (TCP)

A TCP socket is identified by a 4-tuple. The receiving host uses all four values to direct a segment to the right socket:

\[ \text{TCP socket} \;\leftrightarrow\; (\text{source IP},\ \text{source port},\ \text{dest IP},\ \text{dest port}) \]
each connection gets its own socket
source IP = address of the sending host (no unit) · source port = port of the sending socket (no unit) · dest IP = address of the receiving host (no unit) · dest port = port of the receiving socket (no unit)

A server host may support many simultaneous TCP sockets, each identified by its own 4-tuple. A web server, for instance, has a different socket for each connecting client, even though every client sends to the same destination port 80. Two segments that differ in any of the four values go to different sockets.

A non-threaded server creates a new process per connection (P4, P5, P6 in the lecture figure). A threaded web server uses one process with a thread per connection socket; the sockets are still separate and still identified by their 4-tuples.

Part 2 · UDP

Section 5UDP segments

UDP (User Datagram Protocol, RFC 768) is the "no frills", "bare bones" Internet transport protocol. It offers best-effort service: UDP segments may be lost or delivered out of order to the application. It is connectionless: there is no handshaking between UDP sender and receiver, and each UDP segment is handled independently of the others.

Why use it at all? The lecture gives four reasons:

  • No connection establishment, which would add delay.
  • Simple: no connection state at the sender or receiver.
  • Small segment header.
  • No congestion control: UDP can blast away as fast as desired.

UDP is often used for streaming multimedia apps, which are loss tolerant and rate sensitive, and also for DNS and SNMP. If an application needs reliable transfer over UDP, it must add the reliability itself at the application layer (application-specific error recovery).

Analogy

UDP is a postcard: a short "from" and "to" line, a note of how long the card is, a quick smudge check, and the message. Nobody confirms it arrived. That is exactly why it is cheap and fast. The analogy breaks on size: the length field lets a UDP "postcard" carry tens of kilobytes.

Tricky bits
  • The length field includes the 8-byte header. 100 data bytes give a length of 108, not 100.
  • UDP's header is 8 bytes; TCP's minimum header is 20 bytes (Section 7). Do not mix them up.
  • "No congestion control" is listed as a reason for UDP (the app can send as fast as it wants), not as a defect in this lecture.
  • Reliable transfer over UDP is possible, but the application has to do it.

Section 6Internet checksum

The checksum's goal is to detect errors (for example, flipped bits) in a transmitted segment. It detects; it does not correct.

Sender: treat the segment contents as a sequence of 16-bit integers; add them using 1's complement addition; put the 1's complement of the sum into the checksum field.

Receiver: compute the checksum of the received segment and check whether it equals the checksum field value. If not, an error is detected. If yes, no error is detected (which is not the same as "no error": some combinations of flips cancel out).

The one rule that makes it 1's complement arithmetic: when adding, a carry out of the most significant bit is wrapped around and added back into the least significant bit.

\[ \begin{aligned} s &= a + b \quad (\text{17-bit result possible})\\ s' &= (s \bmod 2^{16}) + c \\ \text{checksum} &= \overline{s'} \end{aligned} \]
1's complement sum with wraparound, then invert every bit
\(a, b\) = 16-bit words of the segment (no unit) · \(s\) = ordinary binary sum (no unit) · \(c\) = carry out of bit 15, either 0 or 1 (no unit) · \(s'\) = wrapped 16-bit sum (no unit) · \(\overline{s'}\) = \(s'\) with every bit flipped (no unit)
Example 6 (lecture): adding two 16-bit integers
\(a = 1110\,0110\,0110\,0110\), \(b = 1101\,0101\,0101\,0101\) (16-bit words)

Add them as ordinary binary numbers. The result needs 17 bits; the leading 1 is the carry out of the most significant bit:

\[ \begin{aligned} &\phantom{+}\ \ 1110\,0110\,0110\,0110\\ &+\ \ 1101\,0101\,0101\,0101\\ &= 1\ 1011\,1011\,1011\,1011 \end{aligned} \]

Wrap the carry around: drop it from the left and add 1 to the right end.

\[ \begin{aligned} s' &= 1011\,1011\,1011\,1011 + 1\\ &= 1011\,1011\,1011\,1100 \quad (\text{sum}) \end{aligned} \]

Invert every bit to get the checksum:

\[ \text{checksum} = \overline{1011\,1011\,1011\,1100} = 0100\,0100\,0100\,0011 \]
sum = 1011 1011 1011 1100 · checksum = 0100 0100 0100 0011

Check at the receiver: adding the sum and the checksum gives all ones, \(1011\,1011\,1011\,1100 + 0100\,0100\,0100\,0011 = 1111\,1111\,1111\,1111\), which is what an error-free segment produces.

Filled in

The lecture's receiver rule is "compute the checksum and compare it with the checksum field". The all-ones check above is an equivalent way to do the same test, added here because many exam solutions use it.

Part 3 · TCP reliable transfer

Section 7TCP overview and segment

TCP (RFCs 793, 1122, 1323, 2018, 2581) gives each pair of processes a connection with these properties:

  • Point-to-point: one sender, one receiver.
  • Reliable, in-order byte stream: the application sees a stream of bytes, not separate messages.
  • Pipelined: several segments can be in flight; TCP congestion and flow control set the window size.
  • Send and receive buffers: the application writes into the send buffer and reads from the receive buffer through its socket.
  • Full duplex: data flows in both directions in the same connection. MSS (maximum segment size) is the largest amount of application data in one segment.
  • Connection-oriented: handshaking (exchange of control messages) initializes sender and receiver state before data exchange.
  • Flow controlled: the sender will not overwhelm the receiver.

The segment header is laid out in 32-bit rows:

2sequence number (32 bits)counts bytes of data, not segments

The six flags: URG urgent data (generally not used), ACK the ACK number is valid, PSH push data now (generally not used), and RST, SYN, FIN for connection establishment (setup and teardown commands).

Analogy

The analogy breaks because TCP numbers individual bytes, not pages.

  • Sequence numbers count bytes, not segments.
  • The receive window field is for flow control (receiver's buffer), not congestion control.
  • Minimum TCP header is 20 B; with options it grows in steps of 4 B.
  • Setup and teardown flags are SYN, FIN and RST. URG and PSH are generally not used.

Section 8Sequence numbers and ACKs

TCP views the data as a numbered stream of bytes.

  • Sequence number of a segment: the byte-stream number of the first byte in the segment's data.
  • Acknowledgement number: the sequence number of the next byte expected from the other side.
  • ACKs are cumulative: ACK = 120 says "I have every byte before 120".

How does a receiver handle out-of-order segments? The TCP specification does not say; it is up to the implementor.

\[ \text{ACK} = \text{seq} + L, \qquad \text{seq}_{\text{next}} = \text{seq} + L, \qquad \text{last byte} = \text{seq} + L - 1 \]
for a segment received in order
seq = sequence number of the segment, the number of its first data byte (no unit) · \(L\) = bytes of data in the segment, in bytes (B) · ACK = acknowledgement number the receiver sends back (no unit) · \(\text{seq}_{\text{next}}\) = sequence number of the sender's next segment (no unit)

Section 10Fast retransmit

The timeout period is often relatively long, so a lost segment can sit unresent for a long time. TCP can detect lost segments sooner through duplicate ACKs. A sender often sends many segments back to back; if one is lost, each later segment that arrives makes the receiver repeat its last ACK (it is still waiting for the missing byte). So there will likely be many duplicate ACKs.

Fast retransmit: if the sender receives 3 duplicate ACKs for the same data, it resends the missing segment before its timer expires.

\[ n_{\text{dup}} = 3 \;\Rightarrow\; \text{resend segment with seq} = \text{ACK value} \]
fast retransmit trigger
\(n_{\text{dup}}\) = number of duplicate ACKs, ACKs carrying the same number as an earlier ACK (no unit) · ACK value = the repeated acknowledgement number, which is the first missing byte (no unit)

Part 4 · Flow control and connections

Section 11Flow control

The receive side of a TCP connection has a receive buffer. Data from IP lands in the buffer, and the application process drains it by reading. The application may be slow at reading. Flow control makes sure the sender won't overflow the receiver's buffer by transmitting too much, too fast. It is a speed-matching service: it matches the send rate to the receiving application's drain rate.

How it works (assuming the receiver discards out-of-order segments):

  • The spare room in the buffer is the RcvWindow.
  • The receiver advertises the spare room by including the value of RcvWindow in the segments it sends (the receive window field).
  • The sender limits its unACKed data to RcvWindow. This guarantees the receive buffer doesn't overflow.
  • The receiver can temporarily shut the window: window size = 0 asks the sender to stop transmitting data.
\[ \text{RcvWindow} = \text{RcvBuffer} - B_{\text{buf}} \]
\[ \text{LastByteSent} - \text{LastByteAcked} \le \text{RcvWindow} \]
spare room advertised by the receiver, and the limit it puts on the sender
RcvWindow = spare room in the receive buffer, in bytes (B) · RcvBuffer = total size of the receive buffer, in bytes (B) · \(B_{\text{buf}}\) = data sitting in the buffer, received but not yet read by the application, in bytes (B) · LastByteSent − LastByteAcked = unACKed data in flight, in bytes (B)
Filled in

The sender-side inequality is the lecture's "sender limits unACKed data to RcvWindow" written in the same notation it uses for cwnd (Section 14).

Section 12Handshake and SYN flood

TCP sender and receiver establish a "connection" before exchanging data segments, initializing TCP variables: sequence numbers, buffers and flow control info (for example RcvWindow). The client is the connection initiator (in Java, new Socket("hostname", port)); the server is contacted by the client (welcomeSocket.accept()).

Three-way handshake:

  1. The client sends a SYN segment to the server. It specifies the client's initial sequence number and carries no data.
  2. The server receives the SYN and replies with a SYNACK segment. The server allocates buffers and specifies its own initial sequence number.
  3. The client receives the SYNACK and replies with an ACK segment, which may contain data.
\[ \begin{aligned} \text{SYN:}\quad & \text{SYN}=1,\ \ \text{seq} = \text{client\_isn}\\ \text{SYNACK:}\quad & \text{SYN}=1,\ \ \text{seq} = \text{server\_isn},\ \ \text{ack} = \text{client\_isn}+1\\ \text{ACK:}\quad & \text{SYN}=0,\ \ \text{seq} = \text{client\_isn}+1,\ \ \text{ack} = \text{server\_isn}+1 \end{aligned} \]
the three segments of the handshake
client_isn = client's initial sequence number (no unit) · server_isn = server's initial sequence number (no unit) · SYN = the SYN flag bit, 1 or 0 · ack = acknowledgement number field (no unit)
Example 12a (lecture): the three-way handshake

Connection request: the client sends SYN = 1, seq = client_isn. The SYN consumes one sequence number even though it has no data.

Connection granted: the server answers with SYN = 1, seq = server_isn, ack = client_isn + 1 (the next byte it expects from the client).

ACK: the client sends SYN = 0, seq = client_isn + 1, ack = server_isn + 1. From here on, data flows in both directions.

SYN → SYNACK (ack = client_isn + 1) → ACK (ack = server_isn + 1)

SYN flood attack (a denial of service attack): the attacker sends a large number of TCP SYN segments without completing the third handshake step. The server allocates connection resources for every SYN, so its resources become exhausted and legitimate clients are denied service. Sending SYNs from many sources makes it a DDoS (distributed denial of service) SYN flood.

SYN cookies (RFC 4987) are an effective defense. On receiving a SYN, the server allocates nothing. Instead it creates its initial sequence number (the "cookie") from a hash:

\[ \text{server\_isn} = h(\text{IP}_S,\ \text{IP}_D,\ \text{ports},\ K) \]
\[ \text{ACK valid} \iff h(\ldots) + 1 = \text{ack field of the ACK} \]
SYN cookie: state is kept in the sequence number, not in memory
\(h\) = hash function known to the server · \(\text{IP}_S, \text{IP}_D\) = source and destination IP addresses of the SYN (no unit) · ports = source and destination port numbers of the SYN (no unit) · \(K\) = secret number known only to the server
Example 12b (lecture): checking a returning ACK with no stored state

A legitimate client returns an ACK segment. The server must check that it matches an earlier SYN, but it kept no memory of SYNs. So it runs the same hash on the same fields (the IP addresses and ports, now read from the ACK) with the same secret key.

The client's ACK carries ack = server_isn + 1. If the hash result plus one equals that acknowledgement number, the ACK corresponds to an earlier SYN and is valid. Only then does the server allocate resources.

An attacker who never completes step 3 costs the server nothing but one hash per SYN.

Valid if hash + 1 = ack; resources allocated only after a valid ACK
Analogy

A restaurant that sets a table for everyone who phones for a reservation can be ruined by prank callers who never show up (SYN flood). A SYN cookie is like giving each caller a code computed from their name and a secret; no table is set until someone walks in and quotes a valid code. The analogy breaks because a real restaurant would remember the bookings; the point of the cookie is that the server remembers nothing.

Tricky bits
  • SYNACK's ack is client_isn + 1, even though the SYN carried no data: the SYN uses up one sequence number.
  • The third segment's ack is server_isn + 1, and its seq is client_isn + 1.
  • Only the third segment may carry data; SYN carries none.
  • The SYN flood works because resources are allocated at step 2, before the client proves it exists.

Section 13Closing and TCP states

Closing a connection (the client closes its socket with clientSocket.close()) takes four steps:

  1. The client end system sends a TCP FIN control segment to the server.
  2. The server receives the FIN and replies with an ACK. It then closes the connection and sends its own FIN.
  3. The client receives the FIN and replies with an ACK. It enters a timed wait, during which it will respond with an ACK to any FIN it receives.
  4. The server receives the ACK. The connection is closed.
\[ \text{segments} = \underbrace{3}_{\text{open}} + \underbrace{4}_{\text{close: FIN, ACK, FIN, ACK}} = 7 \]

Part 5 · Congestion control

Section 14Congestion and the windows

Informally, congestion is "too many sources sending too much data too fast for the network to handle". More precisely, congestion occurs when the total arrival rate from all flows exceeds a router's output link capacity. It shows up as:

  • lost packets (buffer overflow at routers), and
  • long delays (queueing in router buffers).

This is different from flow control: flow control protects one receiver, congestion control protects the network. To relieve congestion, the sending nodes should slow down, and TCP does that by reducing its window. The window size is the number of bytes allowed to be in flight simultaneously.

There are two broad approaches:

  1. End-end congestion control: no explicit feedback from the network; congestion is inferred from loss and delay observed at the end systems. This is the approach taken by TCP.
  2. Network-assisted congestion control: routers provide feedback to end systems indicating congestion, as used in Asynchronous Transfer Mode (ATM).

A TCP sender keeps two windows. The receiver window (rwnd) keeps the receiver's buffer from overflowing (flow control, Section 11). The congestion window (cwnd) keeps the sender from overflowing the intermediate routers' buffers (congestion control). The sender obeys the smaller one.

\[ W = \min(\text{rwnd},\ \text{cwnd}), \qquad \text{LastByteSent} - \text{LastByteAcked} \le W \]
\[ \text{rate} \approx \frac{\text{cwnd}}{\text{RTT}}\ \ \frac{\text{bytes}}{\text{s}} \]
actual window and the resulting sending rate
\(W\) = actual window, the most bytes that may be in flight, in bytes (B) · rwnd = receiver window, in bytes (B) · cwnd = congestion window, in bytes (B) or segments (MSS) · RTT = round-trip time, in seconds (s) · rate = sending rate, in bytes per second (B/s)
Filled in

The lecture writes rate \(\approx \frac{\text{cwnd}}{\text{RTT}}\), which assumes cwnd is the smaller window. When rwnd is smaller, the sender is limited by \(W = \text{rwnd}\), so the general form is \(\text{rate} \approx \frac{W}{\text{RTT}}\). The practice problems use this.

How does the sender perceive congestion? A loss event is a timeout or 3 duplicate ACKs. After a loss event the sender reduces its rate (cwnd). cwnd is dynamic, a function of perceived network congestion, governed by three mechanisms: AIMD (Section 15), slow start (Section 16) and being conservative after timeout events (Section 17).

\[ \begin{aligned} \text{rwnd} < \text{cwnd}:&\quad W = \text{rwnd} \ \ (\text{receiver is the bottleneck})\\ \text{cwnd} < \text{rwnd}:&\quad W = \text{cwnd} \ \ (\text{network is the bottleneck}) \end{aligned} \]
The smaller window wins

You send only as many trucks as the tighter limit allows. The analogy breaks because TCP has no traffic report: it guesses cwnd from losses (end-end control).

  • The actual window is the minimum, not the sum and not the maximum.
  • Rate divides by RTT: convert ms to s first. 18 000 B over 60 ms is 300 000 B/s, not 300 B/s.
  • TCP is end-end; network-assisted control (ATM) needs routers to send feedback.

Section 15AIMD

Additive increase, multiplicative decrease (AIMD): increase the transmission rate (window size), probing for usable bandwidth, until loss occurs.

  • Additive increase: increase cwnd by 1 maximum segment size (MSS) every RTT until loss is detected.
  • Multiplicative decrease: cut cwnd in half after loss.

Repeating this gives the saw tooth behavior: TCP keeps probing for bandwidth, backs off by half when it finds the limit, and probes again.

\[ \text{no loss in an RTT: } \text{cwnd} \leftarrow \text{cwnd} + 1\ \text{MSS}, \qquad \text{loss: } \text{cwnd} \leftarrow \frac{\text{cwnd}}{2} \]
AIMD update rules
cwnd = congestion window, in bytes (B) or segments (MSS) · MSS = maximum segment size, in bytes (B) · RTT = round-trip time, in seconds (s)

Section 16Slow start and avoidance

Slow start. When a connection begins, TCP increases its rate exponentially until the first loss event:

  • initially cwnd = 1 MSS;
  • cwnd doubles every RTT;
  • this is done by incrementing cwnd by 1 MSS for every ACK received.

The point is to discover the available bandwidth fast: it is desirable to ramp up quickly to a respectable rate. When cwnd passes a threshold (ssthresh), TCP moves to the congestion avoidance phase to slow down the growth.

Congestion avoidance. Once cwnd is above the threshold, cwnd is incremented by one segment every RTT (that is, for every window of ACKs received): a linear increase. cwnd keeps increasing linearly until loss is detected. TCP spends most of its time in this phase.

\[ \text{slow start: } \text{cwnd}_n = 2^{n}\ \text{MSS}, \qquad n_{\text{ss}} = \log_2\!\left(\frac{\text{ssthresh}}{1\ \text{MSS}}\right) \]
\[ \text{congestion avoidance: } \text{cwnd} = \text{ssthresh} + k\ \text{MSS} \]
window size by round, starting from 1 MSS
\(\text{cwnd}_n\) = congestion window after \(n\) RTTs of slow start, in MSS · \(n\) = number of RTTs since the start (no unit) · ssthresh = slow start threshold, in MSS · \(n_{\text{ss}}\) = RTTs needed to reach ssthresh when it is a power of 2 (no unit) · \(k\) = RTTs spent in congestion avoidance (no unit)

Analogy

  • "Slow" start is the exponential phase. The name refers to starting from 1 MSS, not to slow growth.

Section 17Reacting to loss

At any time, when congestion occurs, TCP decreases the window. It recognizes congestion by two signals, and treats them differently:

1. Three duplicate ACKs. The receiver got all packets up to the gap and is still receiving packets, so the network is at least capable of delivering some segments. This could be temporary congestion, so TCP reduces cwnd, but not aggressively, and stays in congestion avoidance.

2. Timeout. No response from the receiver at all: more likely significant congestion. TCP reduces cwnd aggressively to 1 MSS and goes back to slow start.

\[ \text{3 dup ACKs:}\quad \text{ssthresh} = \frac{\text{cwnd}}{2},\quad \text{cwnd} = \text{ssthresh},\quad \text{stay in congestion avoidance} \]
\[ \text{timeout:}\quad \text{ssthresh} = \frac{\text{cwnd}}{2},\quad \text{cwnd} = 1\ \text{MSS},\quad \text{back to slow start} \]
use cwnd at the moment the loss is detected
cwnd = congestion window, in MSS (or bytes) · ssthresh = threshold between slow start and congestion avoidance, same unit as cwnd · MSS = maximum segment size, in bytes (B)

Most of the time the window looks like a saw tooth: cwnd increases by 1 every RTT and is halved at each loss, and the cycle repeats (AIMD, Section 15).
